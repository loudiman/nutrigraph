# The golden dataset and the eval gate

A behaviour change here is measurable instead of a matter of opinion. About
sixty hand-written cases run against the real graph on every pull request; a
missed Refusal, a missing Citation, an allergen in an answer or a schema failure
stops the merge.

## The three groups

| Group | Count | What it covers | What scores it |
|---|---|---|---|
| safety | 22 | the four refusal subjects, an allergen trap in a Recommendation and one in a Meal, an attempt to make the Coach state a clinical claim, a request framed as a friend's question, and the four bugs found during the build | plain assertions, never a model |
| retrieval | 21 | `ask_question`, each case with a reference answer and a reference context | assertions, and ragas on the prose |
| behaviour | 21 | `log_meal`, `review_day`, `recommend`, `update_profile`, the mixed-intent path, the clarify path, an unmatched food, and a Filipino dish only the local table holds | plain assertions |

**Only the retrieval group pays for a judge.** That is what keeps a whole run at
a few cents and a couple of minutes, which is what makes it affordable on every
pull request. A rule-list Refusal reaches no provider at all.

**Safety is never judged by a model.** A judge can flake; an assertion cannot,
and a flaky safety test is worse than none.

## What a case may assert

Structure, never wording:

- the Intent or Intents the router chose, and the nodes that ran;
- that a Refusal fired, with its subject, its disclaimer, its referral, and the
  help-line where the subject carries one;
- that the citations list is not empty and names the expected document;
- that a named allergen appears nowhere in the answer — and, on `log_meal`, that
  the Coach's own warning *does* name it;
- that the output schema validated and the Turn did not end on a fixed message;
- that the logged Items match the expected foods, quantities and status values;
- that the Profile holds what the Turn said it changed.

There is no `present` assertion, deliberately: a substring of an answer is a
string comparison of prose wearing a schema. The prose is judged by ragas alone,
so a harmless rewording cannot fail a build — which is what keeps people reading
failures instead of dismissing them. `tests/test_eval_gate.py` holds the allowed
key list and fails if a new one appears.

### Two shapes of case

Most cases carry a `message` and drive a whole Turn. A few carry a `draft`
instead: a finished Coach reply, run through the release gate — the medical-claim
scan and then the prose allergen scan, in the order `run_turn` runs them. They
exist because some failures cannot be produced by asking the live graph nicely.
The recommender strikes allergens out in SQL before a model sees a candidate, so
"a Recommendation that names peanut" has no live path; it is still exactly what
the prose half of the allergy check is for, and a draft is how it is tested. No
model runs on these, and nothing about them can flake.

## Where cases come from

**Hand-written, and no case is generated by a model.** A generated expected
answer can encode a mistake as the correct behaviour, and a safety test built
that way is worse than none. The safety cases stay hand-written for ever: you
cannot wait for a real allergen failure in order to write a test for it.

**Then harvested.** A Turn that fails in real use becomes a case. The raw
message is in `message.raw_text`, which the 90-day retention keeps:

```sql
select turn_id, role, raw_text, created_at
  from message
 where turn_id = '<the turn from the trace or the report>'
 order by created_at;
```

Take the User's message verbatim, decide by hand what the correct answer was,
write the structure down as a case in the group it belongs to, and say in `why`
what went wrong. Run it, watch it fail, then fix the behaviour. The set grows
where the system actually broke, which is the cheapest way to find the failures
nobody imagined. Nothing about the harvest is automatic: a model deciding what
the right answer was is the thing this whole file exists to prevent.

## Changing a case

A case is data in this repository.

- **A behaviour change edits its case in the same pull request.** The diff then
  shows the behaviour change and the test change together, and a reviewer sees
  the claim next to the evidence. A pull request that changes behaviour and
  leaves the case alone has either not changed anything or has broken the gate.
- **A safety case change additionally needs a written reason in the pull request
  body**, explaining why the boundary moved. A weakened refusal must never pass
  as a routine test update. The pull request template asks for it directly.

**There is no quarantine list and no way to make one.** A case carrying `skip`,
`quarantine`, `xfail`, `flaky`, `disabled` or `generated_by` is a load error, not
a warning — `dataset.FORBIDDEN_KEYS` is the list, and
`test_a_quarantined_case_is_a_load_error_rather_than_a_warning` is what stops one
being started. A quarantined safety case is a silent hole, and quarantine lists
are rarely emptied. A case that has started flaking is a case to fix.

`--case` and `--group` exist for working on one case on a laptop. The build
passes neither, and a test asserts that it does not: a run that names its cases
is a skip list with the sign flipped.

## The gates

| Check | Effect |
|---|---|
| a missed Refusal, a missing Citation, an allergen in an answer, a schema failure | **always blocks** |
| any other structural assertion | blocks |
| the four ragas means | blocks only on a fall of more than `MARGIN` below the stored baseline |

The baseline is `baseline.json`, and it ratchets: each metric takes the higher of
what is stored and what the run measured, so a change that improves the answers
moves the bar and a change that merely re-rolls the judge's dice does not. A
metric with no baseline yet cannot block, and the first run establishes one.

A fixed pass mark would instead train people to run the pipeline again until it
passed. That is the failure mode this exists to avoid.

**The baseline is committed by a person, not by the build.** A local run
rewrites `baseline.json` when the means improve and says so; commit it with the
change that earned it. The build runs the judge with `--no-write-baseline`,
because a build that pushed to `main` would be moving the bar with nobody
reading it.

## Running it

Two processes, and that is a decision rather than an accident: ragas 0.4 imports
`langchain_community.chat_models.vertexai`, which needs a `langchain-core` below
1.0, and the agent runs on `langchain` 1.x. One environment holding both resolves
to neither. `dataset.py` and `gate.py` therefore import nothing but the standard
library, and the judge reads a JSON file.

```bash
# a throwaway PostgreSQL — never Neon, whose free tier is a ceiling
docker run -d --name eval-pg -p 55432:5432 \
  -e POSTGRES_USER=nutrigraph -e POSTGRES_PASSWORD=nutrigraph \
  -e POSTGRES_DB=nutrigraph_eval pgvector/pgvector:pg17

cd agent
export DATABASE_URL=postgresql://nutrigraph:nutrigraph@127.0.0.1:55432/nutrigraph_eval
export GOOGLE_API_KEY=...          # the key langchain-google-genai reads on its own
export LANGSMITH_TRACING=true
export LANGSMITH_ENDPOINT=https://apac.api.smith.langchain.com   # not the US default

pip install -e .
python -m evals.run --rows rows.json --outcomes outcomes.json

# the judge, in an environment of its own
python -m venv .judge && .judge/bin/pip install -r evals/requirements-judge.txt
.judge/bin/python -m evals.judge rows.json --scores scores.json
```

`--no-prepare` skips the migration, the seed and the Corpus load when the
database already holds them, which is most of the time on a laptop.

`LANGSMITH_ENDPOINT` is required, not a default worth trusting: this account is
on the APAC data plane, and the SDK's US default answers a valid key with a 403
on every call, silently, tracing writes included.

## What the run is, and what it is not

**It runs the real graph**, at the agent turn seam: a `user_id` and a message in,
the same router, rule list, Corpus search, composer and release gate a User
reaches. A golden case answered by a fake proves only that the fake is
consistent.

**One User for each case, and a checkpointer for each case.** A day total is per
User and the cases share a database, so a shared Profile would make one case's
Meal another case's arithmetic.

**The Corpus is `corpus.json`, not the live manifest.** Forty documents fetched
from forty web servers is the slow, flaky step a pull request may not take, and a
Citation can only be asserted against a passage that is the same one every time.
The passages are public-domain United States federal guidance, embedded once per
database.

**FoodData Central is deliberately not wired.** A golden case may not depend on a
third party's search endpoint being up, so the behaviour cases name dishes the
local Filipino table holds — the path this project is actually about — and one
food that nothing anywhere holds. `match_food` already treats an unreachable
food source as an uncounted Item, so nothing special happens for it here.
